# 截图记账与账本问答

更新日期：2026-10-15（Asia/Shanghai）。用户已要求据此重新开发；截图版代码与 APK 已完成首轮实现，手机验收仍未完成。未发布为新 GitHub Issues。

## 已确认的需求

- 用户主动提供支付详情或多笔账单列表截图，App 识别交易并分类记账。
- 用户已选择：清楚的自动入账，缺失、模糊或疑似重复的先确认。
- 用户可以询问账单明细、按条件查询和汇总。
- 实时读取微信不再是主流程，旧采集验证任务不再作为本方案的前置条件。

## 主流程与处理边界

1. 用户在 App 选择截图，使用现有本地中文 OCR 能力识别；只处理主动选择的图片。
2. 按图片中的位置关系区分日期分组、交易明细和汇总。一张图可生成多条采集候选，每日收支合计、余额及界面按钮不得生成正式账单。
3. 提取可读的金额、日期时间、收支方向、交易类型、商户或备注、已有分类。金额使用整数分；缺失值保留为空。
4. 保留图片里明确的分类；已有商户规则可用于分类。无法判断用途时归入“其他”，不按截断商户名编造用途；用户可修改分类。
5. 金额、方向、必要日期和交易状态清楚，通过校验且无疑似重复的交易自动成为正式账单。其余候选展示原因，允许补全、修改、确认或放弃；确认前不计入统计。
6. 同图重复导入要能发现；不同截图重叠、详情和列表交叉出现同一交易时，缺少可靠交易号的疑似重复先确认。不能只凭同金额或同商户删除交易。
7. 正式账单在手机本地保存，支持查看、修改、删除；问答只查询已入账的记录。

截图里的“昨天”是截图内容，不直接等于导入日前一天。用户已确认：只有月日、缺失年份时默认使用当年，可修改默认年份；截图明确显示年份时保留原年份。无法确定完成状态的详情页、待支付、待收款和失败交易先确认或排除，不当作已完成交易。

部分行被遮挡、金额只剩片段时，不用每日合计倒推出缺失交易。列表中的明确历史交易可以主动导入；旧规则“浏览历史详情不触发实时新交易”不应阻止这条主动导入路径。

退款单独记录并抵扣消费，不计作普通收入；没有原交易标识时不猜测对应的消费。个人转账、红包沿用现有收支口径，可改为内部转账并排除统计。

## 2026-10-19 导入体验修复

用户反馈列表和详情均有交易时间丢失、重复确认过多，以及已确认商家分类未沿用的问题。沿用既有公开验证边界，验收行为如下：

- 列表保留时间与商家；识别全角冒号、中文时分秒和一位小时，统一存为 `HH:mm` 或 `HH:mm:ss`。详情优先读取支付／交易时间，支持标签、日期、时间分行；不把手机状态栏时钟当作交易时间。
- 导入和核对使用同一重复判断：结合交易号、日期、金额、方向、类型、商家及时间；双方都有秒时比较秒，分钟精度重叠仍需核对。不同的可靠交易号不因时间金额相近而提示重复。没有可靠交易号的疑似重复仍不自动丢弃。
- 核对时默认记住商家分类，可取消。匹配时忽略商家名中的空白、统一全半角，但不模糊合并不同商家。没有记忆规则时，同商家已入账记录的非“其他”分类一致可用于后续导入；有冲突则不猜。截图明确的非“其他”分类仍优先。
- 不改动已有账单金额、时间或分类，不清空数据或重建数据库；使用人工样例做回归，真实截图 OCR 和手机覆盖安装需实测。

## 账本问答

- 支持按日期范围、分类、商户、方向、交易类型查明细和汇总，例如“这个月餐饮花了多少”“上周有哪些退款”。
- 程序从正式账单查询并用整数分计算金额，回答附对应明细或可查看明细的入口。模型不负责心算或编造交易。
- 回答明确查询范围；没有记录时表示该范围内没有已导入账单，不推断现实中没有消费。待确认记录不混入正式汇总。
- 账本、统计和问答使用同一退款及内部转账口径。日期或查询含义不清楚时先澄清。
- 保留既有 DeepSeek 作为后续文本理解方案；不假定其图片能力，不因截图导入配置密钥。云端调用实施前沿用既有密钥保护和最少必要文本规则。
- 聊天新增、修改和删除沿用先预览、用户确认后执行的约定；本轮用户确认的是截图自动入账规则。

## 数据与隐私

沿用 Kotlin、Compose、Material 3、Android 12+、Room 正式账本和暖色界面。OCR 优先沿用已集成的本地中文识别，不依赖通知监听、无障碍或后台读取。

主动导入图片与旧版无障碍截屏开关是不同入口；旧版 OCR 保持关闭的选择不阻止用户主动选择图片识别。不得因此擅自开启无障碍截屏。

截图默认只用于当次本地识别，不自动上传或复制到长期存储；用户原相册文件不删除。交易记录可本地保存和清除，不自动云备份。微信原文、截图、真实交易数据、设备导出和密钥不提交 Git，也不发布到 Issues；验证使用人工构造的替代样例。

## 开发顺序

以下为实施顺序，不代表已发布任务或完成手机验收。原规格和 #2–#6 Issues 保留历史状态，不直接改写或关闭。

1. **截图导入、核对与本地账本**（无实时采集依赖）：从选择图片、逐笔识别到保存和查看，清楚的自动入账、存疑的待确认，重启后数据仍在；支持纠正和删除。
2. **去重、分类与统计完善**（依赖 1）：验证重复图片、重叠截图、连续同金额真实交易；完善可修改分类、退款和内部转账口径，展示月度与分类统计。
3. **账本问答**（依赖 1、2）：查询真实记录并返回一致的汇总和明细，处理空结果、日期歧义、非法模型输出和网络失败；聊天写操作先确认。
4. **小米 15 安装与更新验收**（依赖 1–3）：验证相册选择、图片识别、确认纠错、去重、问答和更新后账本保留。没有实测结果时不得声称兼容。

## 验证边界

沿用现有三个公开行为边界，按 TDD 实施，第一条改为主动图片导入：

- **截图识别结果 → 采集候选／正式账单**：单笔与多笔、日期分组、合计排除、缺失年份、遮挡金额、完成状态和分类。
- **入账与确认 → 列表和统计**：自动入账、人工确认、取消、纠错、删除、重复与冲突、退款、内部转账和重启持久化。
- **聊天问题 → 查询结果或待确认修改**：数据库与回答一致、能追溯明细、空结果、歧义、取消及失败不改变账本。

解析、Room 持久化与 Compose 页面流程测试不能替代真实图片 OCR、图片选择器及手机安装验收。当前实现包含本地常用查询和默认关闭的可选 DeepSeek 只读条件理解；没有在开发机配置密钥或执行真实模型请求。构建、测试和 APK 检查证据见 HANDOFF.md；手机验收步骤见 `screenshot-validation.md`。
